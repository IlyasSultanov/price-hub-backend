# ТЗ: PriceHub — платформа агрегации прайс-листов поставщиков

**Версия:** 1.0
**Тип проекта:** учебно-боевой pet-project промышленного уровня
**Стек:** Python 3.12+, FastAPI, PostgreSQL, Redis, RabbitMQ/Kafka, Celery/Taskiq, S3(MinIO), Docker, Nginx, GitHub Actions

---

## 1. Суть проекта

Поставщики (магазины, дистрибьюторы) загружают прайс-листы в разных форматах — CSV, XLSX, PDF, XML. Платформа асинхронно парсит их, нормализует товарные позиции, сопоставляет с внутренним каталогом, применяет правила ценообразования и публикует итоговые цены. Наружу торчит публичный REST API каталога с высоким RPS, которым пользуются клиенты-интеграторы, плюс вебхуки об изменении цен.

**Почему именно такой домен для обучения:**

| Требование к обучению | Как закрывается доменом |
|---|---|
| Тяжёлая фоновая обработка | Парсинг файлов на 500 МБ / 5 млн строк |
| Высокий RPS на чтение | Публичный каталог-API, поиск, батч-запрос цен |
| Нетривиальная работа с БД | 20+ млн SKU, партиционирование, история цен |
| Кэши | Горячие товары, результаты поиска, идемпотентность |
| Брокер сообщений | События `price.changed` → вебхуки, аналитика, реиндекс |
| Внешние сервисы | Курсы валют, OCR, email/вебхуки клиентам |
| Сложные тесты | Парсеры, конкурентные обновления, contract-тесты |

---

## 2. Глоссарий

- **Supplier (поставщик)** — организация, поставляющая прайс-лист.
- **Feed (фид)** — конкретная загрузка прайс-листа: файл + метаданные + результат обработки.
- **Raw Item** — сырая строка из файла до нормализации.
- **Offer (оффер)** — нормализованная позиция поставщика: SKU, цена, остаток, валюта.
- **Product (товар)** — каноническая карточка во внутреннем каталоге.
- **Matching** — процесс сопоставления оффера с товаром каталога.
- **Mapping profile** — правила разбора конкретного формата поставщика (какая колонка = цена и т.д.).
- **Publication** — публикация подготовленных цен в read-модель, доступную публичному API.

## 4. Функциональные требования

### M1. Приём файлов

- **FR-1.1.** Загрузка файла через `POST /api/v1/feeds` (multipart) размером до **1 ГБ**. Файл не должен целиком попадать в память приложения — потоковая запись в объектное хранилище.
- **FR-1.2.** Альтернативный сценарий: выдача **presigned URL** для прямой загрузки в S3, минуя приложение. Клиент затем подтверждает загрузку через `POST /api/v1/feeds/{id}/complete`.
- **FR-1.3.** Поддерживаемые форматы: `.csv`, `.tsv`, `.xlsx`, `.xml` (YML/Yandex Market), `.pdf`, а также архивы `.zip`/`.gz` с одним из этих файлов внутри.
- **FR-1.4.** Валидация до постановки в очередь: MIME-тип по сигнатуре файла (не по расширению), размер, квота поставщика, вычисление SHA-256.
- **FR-1.5.** **Дедупликация:** если фид с тем же хэшем от того же поставщика обработан за последние 24 часа — вернуть ссылку на существующий фид со статусом `duplicate`, не запуская обработку.
- **FR-1.6.** **Идемпотентность:** заголовок `Idempotency-Key`; повторный запрос с тем же ключом в течение 24 часов возвращает исходный ответ из Redis.
- **FR-1.7.** Периодический pull: для поставщика можно настроить расписание (cron) забора файла по HTTP(S)/FTP/SFTP.

### M2. Парсинг и нормализация

- **FR-2.1.** Обработка файла в фоне, статусная модель фида:
  `uploaded → queued → parsing → validating → matching → pricing → publishing → completed`
  плюс терминальные `failed`, `partially_completed`, `cancelled`.
- **FR-2.2.** Парсинг **потоковый и чанковый**: файл читается частями (по 5–10 тыс. строк), память воркера не должна расти линейно от размера файла. Пиковое потребление RAM на воркер — не более 512 МБ независимо от размера файла.
- **FR-2.3.** **CSV/TSV:** автоопределение кодировки (UTF-8/CP1251) и разделителя, поддержка кавычек, многострочных значений, BOM. Битые строки не роняют обработку, а попадают в отчёт об ошибках.
- **FR-2.4.** **XLSX:** чтение в режиме read-only/streaming (без загрузки всей книги в память), поддержка нескольких листов, объединённых ячеек, дат и чисел, сохранённых как строки.
- **FR-2.5.** **PDF:** извлечение табличных данных; если текстовый слой отсутствует — постановка в отдельную тяжёлую очередь на OCR через внешний сервис. Обязательна поддержка многостраничных таблиц с повторяющимися шапками.
- **FR-2.6.** **Mapping-профиль:** декларативное описание соответствия колонок полям оффера, с трансформациями (`trim`, `to_decimal`, `replace_comma`, `strip_currency`, `regex_extract`). Профиль версионируется; при обработке фиксируется версия применённого профиля.
- **FR-2.7.** Автоопределение колонок при первой загрузке: эвристика по заголовкам и по содержимому первых 100 строк, с предложением профиля менеджеру на подтверждение.
- **FR-2.8.** Нормализация значений: цены — только `Decimal`, никогда `float`; приведение валют, единиц измерения, очистка названий, нормализация артикулов и штрихкодов (EAN-13 с проверкой контрольной суммы).
- **FR-2.9.** **Отчёт об ошибках:** по каждой отклонённой строке — номер строки, поле, код ошибки, исходное значение. Отчёт доступен для скачивания как CSV; в БД хранятся первые 10 000 ошибок, остальное — счётчиком по кодам.
- **FR-2.10.** **Возобновляемость:** при падении воркера обработка продолжается с последнего закоммиченного чанка, а не с начала файла.
- **FR-2.11.** Отмена: `POST /api/v1/feeds/{id}/cancel` — воркер проверяет флаг отмены между чанками и корректно завершает работу.

### M3. Матчинг с каталогом

- **FR-3.1.** Каскад стратегий: точное совпадение по штрихкоду → по паре (бренд, артикул производителя) → нечёткий поиск по нормализованному названию (полнотекстовый поиск + триграммы) → пусто.
- **FR-3.2.** Каждому матчу присваивается `confidence` (0.0–1.0). Ниже порога (по умолчанию 0.75) — позиция уходит в очередь ручной модерации, а не публикуется автоматически.
- **FR-3.3.** Решения модератора сохраняются как правила и применяются автоматически при следующих загрузках того же поставщика.
- **FR-3.4.** Матчинг батчами: один SQL-запрос на 1000 позиций, а не запрос на позицию (защита от N+1).

### M4. Ценообразование и публикация

- **FR-4.1.** Правила наценки: по поставщику, категории, диапазону закупочной цены. Поддержка процентной и фиксированной наценки, округления до «красивой» цены.
- **FR-4.2.** Конвертация валют по курсу на дату фида (внешний источник + кэш + фолбэк на последний известный курс).
- **FR-4.3.** Выбор лучшего предложения: при нескольких офферах на один товар — по цене с учётом наличия и рейтинга поставщика.
- **FR-4.4.** **Публикация атомарна на уровне фида:** новые цены становятся видны публичному API только после успешного завершения всей обработки. Частичная публикация недопустима.
- **FR-4.5.** История цен: каждое изменение цены товара пишется в таблицу истории для аналитики и графиков.
- **FR-4.6.** **Защита от аномалий:** если фид меняет более 40% цен более чем на 50%, публикация блокируется и уходит на ручное подтверждение (защита от битого прайса).

### M5. Публичный API каталога (горячий путь)

- **FR-5.1.** `GET /api/v1/products/{id}` — карточка с актуальной ценой.
- **FR-5.2.** `GET /api/v1/products` — поиск с фильтрами (категория, бренд, диапазон цен, наличие), **курсорная пагинация** (не `OFFSET`).
- **FR-5.3.** `POST /api/v1/prices/batch` — цены по списку до 500 идентификаторов за один запрос.
- **FR-5.4.** `GET /api/v1/products/{id}/price-history` — история цен за период.
- **FR-5.5.** Rate limiting по API-ключу, разные тарифы (например, 100/1000/5000 запросов в минуту), заголовки `X-RateLimit-*` и `Retry-After`.
- **FR-5.6.** Условные запросы: `ETag` / `If-None-Match` для отдачи `304`.

### M6. Уведомления и вебхуки

- **FR-6.1.** SSE или WebSocket-канал прогресса обработки фида: `GET /api/v1/feeds/{id}/events` (проценты, текущая стадия, счётчики).
- **FR-6.2.** Вебхуки клиентам на события `feed.completed`, `feed.failed`, `price.changed`, `product.out_of_stock`.
- **FR-6.3.** Доставка вебхуков **с гарантией at-least-once**: подпись тела HMAC-SHA256, ретраи с экспоненциальным бэкоффом (1м, 5м, 15м, 1ч, 6ч), отключение эндпоинта после 20 подряд неудач, dead letter queue.
- **FR-6.4.** Email-уведомления менеджеру поставщика об итогах обработки со ссылкой на отчёт об ошибках.

### M7. Аналитика и отчёты

- **FR-7.1.** Дашборд поставщика: количество фидов, доля ошибок, доля сматченных позиций, динамика.
- **FR-7.2.** Генерация отчётов в фоне (CSV/XLSX) с выгрузкой в S3 и presigned-ссылкой на скачивание, живущей 1 час.
- **FR-7.3.** Ежедневный агрегат по срезам (поставщик × категория) для быстрых дашбордов — материализованное представление или отдельная таблица, обновляемая по расписанию.

### M8. Административные функции

- **FR-8.1.** CRUD поставщиков, API-ключей, квот, mapping-профилей.
- **FR-8.2.** Просмотр очередей: длина, количество задач в работе, зависшие задачи, ручной перезапуск.
- **FR-8.3.** Feature flags для включения/выключения дорогих подсистем без релиза.
- **FR-8.4.** Аудит-лог значимых действий (кто, что, когда, откуда).

## 5. Нефункциональные требования

### 5.1 Производительность

| Метрика | Целевое значение |
|---|---|
| `GET /products/{id}` (кэш-хит) | p95 < 25 мс, p99 < 60 мс |
| `GET /products` (поиск) | p95 < 150 мс, p99 < 400 мс |
| `POST /prices/batch` (500 позиций) | p95 < 250 мс |
| Пропускная способность каталог-API | ≥ 2000 RPS на 3 репликах |
| Приём файла 500 МБ | загрузка ≤ 60 с, немедленный ответ `202 Accepted` |
| Полная обработка 5 млн строк CSV | ≤ 10 минут при 4 воркерах |
| Обработка PDF на 200 страниц | ≤ 3 минут |
| Время от завершения фида до вебхука | p95 < 5 с |

### 5.2 Масштаб данных

- Поставщиков: до 500.
- Товаров в каталоге: до 20 млн.
- Офферов: до 60 млн.
- Записей истории цен: до 2 млрд (обязательно партиционирование по времени).
- Фидов в сутки: до 5 000.

### 5.3 Надёжность

- Доступность каталог-API: 99.9%; админ-панели: 99.5%.
- **RPO** (допустимая потеря данных): 5 минут. **RTO** (время восстановления): 30 минут.
- Ни одна задача не теряется при рестарте воркера: подтверждение сообщений только после успешного выполнения.
- Все фоновые задачи **идемпотентны** — повторный запуск не приводит к дублям или двойной наценке.
- Graceful shutdown: при `SIGTERM` приложение перестаёт принимать новые запросы, доживает открытые, воркер доделывает текущий чанк — с таймаутом 30 с.

### 5.4 Ограничения окружения

- Приложение **stateless**: любое состояние — в Postgres, Redis или S3. Никаких локальных файлов между запросами.
- Горизонтальное масштабирование добавлением реплик API и воркеров без изменения конфигурации.
- Конфигурация только через переменные окружения (12-factor), валидация на старте через `pydantic-settings`; приложение падает при некорректном конфиге, а не работает наполовину.

### 6.2 Разделение брокеров (важно понять разницу)

- **RabbitMQ** (или Redis как брокер на старте) — **очередь задач**: «сделай работу». Точка-точка, ack после выполнения, ретраи, приоритеты, отдельные очереди по весу задач.
- **Kafka** — **шина событий**: «случился факт». Несколько независимых потребителей одного события (аналитика, вебхуки, реиндекс), реплей истории, гарантированный порядок в пределах партиции.

На первом этапе допустимо начать только с RabbitMQ + Celery, Kafka добавить на этапе 4 — но архитектуру событий заложить сразу через outbox.

### 6.3 Transactional Outbox

Критично для консистентности: нельзя записать в БД и отправить в брокер атомарно. Поэтому:

1. В одной транзакции с бизнес-данными пишем событие в таблицу `outbox_events`.
2. Отдельный процесс-релей читает необработанные записи и публикует их в Kafka.
3. После подтверждения публикации помечает запись отправленной.

Потребители обязаны быть идемпотентными (дедупликация по `event_id`), поскольку доставка at-least-once.

### 6.4 Разделение очередей по весу

| Очередь | Задачи | Приоритет | Concurrency |
|---|---|---|---|
| `parse.fast` | CSV/XLSX до 50 МБ | высокий | 8 |
| `parse.heavy` | файлы > 50 МБ, PDF, OCR | низкий | 2 |
| `match` | матчинг батчей | средний | 6 |
| `notify` | вебхуки, email | высокий | 12 |
| `reports` | генерация отчётов | низкий | 2 |
| `maintenance` | очистка, агрегаты, партиции | низкий | 1 |

Одна тяжёлая задача не должна блокировать доставку вебхуков — в этом весь смысл разделения.

### 7.2 Требования к БД

- **DB-1.** Все денежные поля — `NUMERIC(14,4)`, в Python — `Decimal`. `float` для денег запрещён.
- **DB-2.** Все временные метки — `TIMESTAMPTZ` в UTC.
- **DB-3.** Первичные ключи — `BIGSERIAL` для больших таблиц, `UUID v7` для внешних идентификаторов, чтобы не раскрывать объёмы и сохранять сортируемость.
- **DB-4.** `price_history` партиционируется по месяцам; создание будущих партиций и отцепление старых — периодической задачей.
- **DB-5.** Индексы обязательны под каждый сценарий чтения: GIN по `search_vector`, `pg_trgm` по `title_normalized`, составные индексы под фильтры каталога, частичные индексы для «активных» записей.
- **DB-6.** Все миграции — через Alembic, обратимые, без блокирующих операций на больших таблицах: `CREATE INDEX CONCURRENTLY`, добавление колонок без `DEFAULT` на миллионных таблицах, `lock_timeout` в миграциях.
- **DB-7.** Массовая вставка офферов — через `COPY` или `execute_values`, не построчный `INSERT`.
- **DB-8.** Конкурентные обновления — через `SELECT ... FOR UPDATE SKIP LOCKED` или оптимистические блокировки по версии. Порядок захвата блокировок фиксирован для исключения дедлоков.
- **DB-9.** Разделение соединений: публичный API читает с реплики, воркеры пишут в primary. Отдельные пулы, ограничение размера пула с учётом числа реплик (`max_connections` Postgres не резиновый — при 10 репликах по пулу 20 это уже 200 коннектов; рассмотреть PgBouncer).
- **DB-10.** Ни одного запроса без `LIMIT` на пользовательских данных. Statement timeout на уровне роли.

## 8. Контракт API

### 8.1 Общие правила

- Версионирование в пути: `/api/v1/...`.
- Ответы об ошибках в формате RFC 9457 (Problem Details):
  ```json
  {
    "type": "https://pricehub.dev/errors/validation",
    "title": "Validation failed",
    "status": 422,
  ```

- Long-running операции возвращают `202 Accepted` + `Location` на ресурс статуса.
- Списки — только курсорная пагинация: `?cursor=...&limit=50`, ответ содержит `next_cursor`.

## 9. Асинхронная обработка

- **AS-1.** Конвейер обработки фида разбит на отдельные задачи, связанные цепочкой: `download → detect_format → parse_chunk(N) → validate → match → price → publish → notify`. Одна гигантская задача на всё запрещена.
- **AS-2.** Каждая задача принимает **идентификаторы, а не объекты**. Передавать в задачу целый файл или ORM-модель нельзя — только `feed_id` и смещение чанка.
- **AS-3.** Ретраи с экспоненциальным бэкоффом и джиттером. Максимум попыток — 5. Разделение ошибок:
  - **retryable** (сеть, таймаут, временная недоступность внешнего API) — ретраим;
  - **permanent** (битый файл, неверный формат, нарушение бизнес-правила) — сразу в `failed`, без ретраев.
- **AS-4.** Все задачи имеют жёсткий таймаут (`soft` + `hard`); зависшая задача убивается и логируется.
- **AS-5.** Dead Letter Queue для окончательно упавших задач, с возможностью ручного перезапуска из админки.
- **AS-6.** Распределённая блокировка через Redis (например, Redlock-подобная схема) для операций, которые не должны выполняться параллельно на одном фиде или поставщике. Обязателен TTL и владелец блокировки, чтобы падение воркера не заблокировало ресурс навсегда.
- **AS-7.** Периодические задачи (beat): pull-фидов по расписанию, обновление курсов валют, создание партиций, очистка старых файлов из S3, пересчёт агрегатов, ретраи вебхуков. Beat запускается ровно в одном экземпляре (лидер-элекшн или отдельный деплой с `replicas: 1`).
- **AS-8.** Прогресс обработки пишется в Redis и отдаётся через SSE; в БД пишутся только контрольные точки, не каждый процент.

## 11. Стратегия кэширования

| Что кэшируем | Ключ | TTL | Инвалидация |
|---|---|---|---|
| Карточка товара с ценой | `product:v1:{id}` | 5 мин | явно, по событию `price.changed` |
| Результаты поиска | `search:v1:{hash(params)}` | 60 с | по TTL |
| Курсы валют | `fx:{date}:{pair}` | 12 ч | по TTL + фолбэк на stale |
| Ответ по Idempotency-Key | `idem:{key}` | 24 ч | по TTL |
| Счётчики rate limit | `rl:{api_key}:{window}` | окно | по TTL |
| Прогресс фида | `feed:progress:{id}` | 1 ч | по завершении |
| Распределённые блокировки | `lock:{resource}` | 5 мин | освобождение владельцем |

**Требования:**

- **CA-1.** Версия схемы в ключе (`v1`) — чтобы менять формат значений без массовой инвалидации.
- **CA-2.** Защита от **cache stampede**: при промахе один запрос идёт в БД под блокировкой, остальные ждут результат или получают stale-значение.
- **CA-3.** Защита от **cache penetration**: отрицательное кэширование несуществующих идентификаторов с коротким TTL.
- **CA-4.** Защита от **cache avalanche**: джиттер к TTL (±10%), чтобы миллион ключей не протух одновременно.
- **CA-5.** Кэш — не источник истины. Полное падение Redis обязано деградировать сервис по скорости, но не по корректности; ответ на недоступность Redis — не `500`.
- **CA-6.** В метриках обязателен hit ratio по типам ключей.

## 12. Внешние сервисы и устойчивость

Интеграции: курсы валют (например, ЦБ/exchangerate API), OCR-сервис, SMTP/email-провайдер, S3, вебхуки клиентов.

- **EX-1.** У каждого HTTP-клиента обязателен явный таймаут — connect и read раздельно. Запросов без таймаута быть не должно.
- **EX-2.** **Circuit breaker** на каждую внешнюю зависимость: после N ошибок подряд цепь размыкается на T секунд, запросы отбиваются мгновенно, затем half-open проба.
- **EX-3.** Ретраи только идемпотентных операций, с бэкоффом и джиттером; для неидемпотентных — идемпотентный ключ на стороне провайдера.
- **EX-4.** **Bulkhead:** отдельный пул соединений и ограничение параллелизма на каждую зависимость, чтобы медленный OCR не выел все воркеры.
- **EX-5.** **Fallback:** недоступен курс валют — берём последний известный и помечаем цену как рассчитанную по устаревшему курсу.
- **EX-6.** Один переиспользуемый `AsyncClient` на процесс (создание клиента на каждый запрос — типичная утечка производительности).
- **EX-7.** В тестах внешние сервисы не вызываются никогда — только моки или `respx`/`WireMock`.

## 13. Безопасность

- **SEC-1.** Аутентификация: JWT (access 15 мин / refresh 30 дней с ротацией и отзывом) для людей, API-ключи для машин. Ключи хранятся только в виде хэша, при создании показываются один раз.
- **SEC-2.** Авторизация на уровне ресурса: поставщик видит только свои фиды. Проверка владения — в слое сервиса, не только в роутере.
- **SEC-3.** Пароли — Argon2id.
- **SEC-4.** Rate limiting на трёх уровнях: Nginx (по IP), приложение (по ключу/тарифу), отдельный жёсткий лимит на загрузку файлов.
- **SEC-5.** Безопасная работа с файлами: проверка сигнатуры, защита от zip-бомб (лимит коэффициента распаковки и итогового размера), защита от XXE при парсинге XML, обработка файлов в изолированном контейнере без доступа к внутренней сети.
- **SEC-6.** Никаких секретов в образах и репозитории; в CI — секреты раннера, в проде — секреты оркестратора или vault.
- **SEC-7.** Валидация всего входа через Pydantic-схемы; ORM-запросы только параметризованные.
- **SEC-8.** Заголовки безопасности на Nginx: HSTS, `X-Content-Type-Options`, `X-Frame-Options`, CSP для админки. CORS — белый список, не `*`.
- **SEC-9.** PII и секреты не попадают в логи — маскирование на уровне процессора логгера.
- **SEC-10.** Контейнеры запускаются от непривилегированного пользователя, файловая система по возможности read-only.
- **SEC-11.** В CI — сканирование зависимостей (`pip-audit`) и образов (Trivy); сборка падает при критических уязвимостях.

## 14. Наблюдаемость

### 14.1 Логи

- Структурированные JSON-логи (`structlog`), обязательные поля: `timestamp`, `level`, `logger`, `message`, `request_id`, `trace_id`, `user_id`, `feed_id`.
- `request_id` генерируется в middleware, прокидывается через `contextvars` и передаётся в фоновые задачи через заголовки сообщения.
- Уровни осмысленно разделены: `INFO` — бизнес-события, `WARNING` — деградации и ретраи, `ERROR` — только то, на что надо смотреть человеку.

### 14.2 Метрики (Prometheus)

**Технические:** RPS, латентность по перцентилям и эндпоинтам, доля 5xx, использование пула БД, длительность запросов к БД, hit ratio кэша, длина очередей, время ожидания задачи в очереди, длительность выполнения задач, состояние circuit breaker.

**Бизнесовые:** фидов обработано за час, средняя длительность обработки, доля битых строк, доля сматченных позиций, количество ценовых аномалий, доля успешных вебхуков.

### 14.3 Трассировка

OpenTelemetry со сквозным `trace_id`: HTTP-запрос → задача в брокере → запросы к БД и внешним сервисам → событие в Kafka → потребитель. Экспорт в Jaeger или Tempo.

### 14.4 Алерты

| Условие | Severity |
|---|---|
| Доля 5xx > 1% за 5 минут | critical |
| p99 каталог-API > 1 с за 10 минут | warning |
| Длина `parse.heavy` > 500 и растёт 15 минут | warning |
| Ни одного успешного фида за 2 часа в рабочее время | critical |
| Реплика Postgres отстаёт > 30 с | critical |
| Свободное место на диске < 15% | warning |
| Circuit breaker разомкнут > 5 минут | warning |

## 15. Тестирование

- **T-1.** Покрытие: не менее 80% общего, не менее 95% для парсеров, ценообразования и матчинга.
- **T-2. Unit-тесты** — чистая логика без БД и сети: трансформации значений, правила наценки, нормализация штрихкодов, стратегии матчинга, вычисление бэкоффа.
- **T-3. Интеграционные тесты** — на **реальных зависимостях в контейнерах** (`testcontainers`): Postgres, Redis, RabbitMQ, MinIO. Мокать БД не нужно, это даёт ложную уверенность.
- **T-4.** Каждый тест выполняется в транзакции с откатом либо на изолированной схеме; тесты обязаны проходить в произвольном порядке и параллельно (`pytest-xdist`).
- **T-5. Фикстуры данных** через фабрики (`polyfactory`/`factory-boy`), а не портянки SQL.
- **T-6. Тесты парсеров** на корпусе реальных проблемных файлов: CP1251, BOM, точка с запятой как разделитель, запятая как десятичный разделитель, пустые строки посреди файла, объединённые ячейки, PDF без текстового слоя, PDF с таблицей на 5 страниц, файл на 1 млн строк (в отдельной медленной группе).
- **T-7. Тесты на конкурентность:** два фида на одного поставщика одновременно; два воркера, взявших один чанк; отмена во время обработки.
- **T-8. Тесты идемпотентности:** повторный запуск любой задачи не меняет итоговое состояние.
- **T-9. Тесты отказов:** Redis недоступен, внешний API отвечает 500, соединение с БД оборвалось, воркер убит по SIGKILL посреди обработки — сервис должен деградировать предсказуемо.
- **T-10. Contract-тесты** публичного API: схема OpenAPI фиксируется снапшотом, изменение схемы без явного апдейта снапшота ломает сборку.
- **T-11. Нагрузочное тестирование** (k6 или Locust) в отдельном пайплайне: сценарий на 2000 RPS по каталогу и параллельная заливка тяжёлого фида. Фиксируются p95/p99 и потребление ресурсов; результаты сохраняются между прогонами для отслеживания регрессий.
- **T-12. Мутационное тестирование** ценообразования (`mutmut`) — опционально, но очень полезно для понимания качества тестов.

## 16. Инфраструктура и деплой

### 16.1 Docker

- Multi-stage сборка, финальный образ — `python:3.12-slim`, без компиляторов и dev-зависимостей.
- Целевой размер образа: < 300 МБ.
- Кэширование слоёв: зависимости ставятся отдельным слоем до копирования кода.
- Непривилегированный пользователь, `HEALTHCHECK`, корректная обработка сигналов (init-процесс или `exec`-форма `CMD`).
- Один образ на все роли (api/worker/beat), роль задаётся командой запуска — так гарантируется идентичность кода.

### 16.2 Nginx

- TLS-терминация, HTTP/2, редирект с HTTP.
- `client_max_body_size 1g`, настроенные `proxy_read_timeout` и буферизация для больших загрузок; для потоковой заливки — `proxy_request_buffering off`.
- `limit_req_zone` и `limit_conn_zone` по IP как первый рубеж защиты.
- gzip/brotli для JSON-ответов, отдача статики и отчётов напрямую (`X-Accel-Redirect` для приватных файлов из S3).
- Проброс `X-Request-ID`, `X-Forwarded-For`, `X-Forwarded-Proto`; в приложении — доверие прокси-заголовкам только от известных адресов.
- Отключён `server_tokens`, метрики и админка закрыты от внешнего мира.
- Отдельный `upstream` с `keepalive` к бэкендам.

### 16.3 Окружения

| Окружение | Назначение | Запуск |
|---|---|---|
| `local` | разработка | docker compose, hot reload, MinIO вместо S3 |
| `test` | CI | docker compose + testcontainers |
| `staging` | предпрод | как прод, уменьшенные ресурсы, реальные внешние сервисы в sandbox |
| `production` | прод | оркестратор, реплики, автоскейл |

### 16.4 Деплой

- **DEP-1.** Zero-downtime: rolling update, readiness-проба, graceful shutdown с `preStop`-задержкой.
- **DEP-2.** Миграции применяются отдельным шагом до выката новой версии кода; **все миграции обратно совместимы** — старая и новая версия кода должны одновременно работать на новой схеме (паттерн expand/contract).
- **DEP-3.** Возможность быстрого отката на предыдущую версию образа.
- **DEP-4.** Резервное копирование Postgres: ежедневный полный дамп + WAL-архивирование; **обязательна регулярная проверка восстановления** — бэкап, который не восстанавливали, не существует.
- **DEP-5.** Ресурсные лимиты (CPU/RAM) заданы для всех контейнеров; воркеру тяжёлой очереди — больше памяти.
- **DEP-6.** Автоскейл воркеров по длине очереди, API — по CPU и RPS.

### 16.5 CI/CD (GitHub Actions)

**Pipeline на pull request:**

1. `lint` — ruff (линт + формат), mypy в строгом режиме.
2. `security` — pip-audit, gitleaks (поиск утёкших секретов).
3. `test-unit` — быстрые тесты, параллельно.
4. `test-integration` — тесты с сервисами в контейнерах.
5. `coverage` — падение сборки при покрытии ниже порога.
6. `build` — сборка образа, сканирование Trivy, публикация в registry с тегом по SHA коммита.
7. `migrations-check` — прогон миграций up/down на чистой БД; проверка отсутствия расхождения моделей и миграций.

**Pipeline на merge в main:**

8. Деплой на staging.
9. Smoke-тесты на staging.
10. Нагрузочный тест (по расписанию, не на каждый коммит).
11. Ручное подтверждение → деплой в production.
12. Уведомление в Slack/Telegram с ссылкой на дашборд.

**Дополнительно:** кэш зависимостей между запусками, matrix-тесты на нескольких версиях Python, обязательные проверки в branch protection, автоматическое версионирование по conventional commits.

## 17. Дорожная карта

Порядок принципиален: сначала работающий вертикальный срез, потом усложнение. Не начинай с Kafka и Kubernetes — начни с одного эндпоинта, который реально принимает файл.

### Этап 1. Скелет (1 неделя)
Структура проекта по слоям (routers → services → repositories), конфигурация через pydantic-settings, SQLAlchemy 2.0 async + Alembic, docker-compose с Postgres и Redis, health-эндпоинты, структурированные логи, CRUD поставщиков, первые тесты с testcontainers, CI с линтом и тестами.
**Готово, когда:** `docker compose up` поднимает всё одной командой, CI зелёный.

### Этап 2. Первый вертикальный срез (1–2 недели)
Загрузка CSV → S3(MinIO) → задача Celery → парсинг → сохранение офферов → статус фида. SSE-прогресс. Отчёт об ошибках.
**Готово, когда:** файл на 100 тыс. строк проходит весь путь и статус виден клиенту.

### Этап 3. Устойчивость обработки (1–2 недели)
Чанковый парсинг, возобновление после падения, идемпотентность задач, ретраи с классификацией ошибок, DLQ, отмена, распределённые блокировки, разделение очередей по весу, XLSX и PDF-парсеры.
**Готово, когда:** воркер, убитый посреди файла на 2 млн строк, после рестарта корректно доводит обработку без дублей.

### Этап 4. Каталог и горячий путь (2 недели)
Матчинг, ценообразование, публикация, read-модель `product_prices`, публичный API с курсорной пагинацией и полнотекстовым поиском, кэширование со всеми защитами, rate limiting, ETag.
**Готово, когда:** нагрузочный тест держит 2000 RPS с p99 < 400 мс.

### Этап 5. События и интеграции (1–2 недели)
Transactional outbox, Kafka, потребители, вебхуки с подписью и ретраями, внешние API с circuit breaker и фолбэками, email-уведомления.
**Готово, когда:** событие изменения цены доходит до клиентского вебхука, а падение внешнего API не роняет обработку фидов.

### Этап 6. Наблюдаемость (1 неделя)
Prometheus + Grafana с дашбордами, OpenTelemetry со сквозной трассировкой, Sentry, алерты, /metrics.
**Готово, когда:** по `trace_id` из ответа API видна вся цепочка вплоть до запроса в БД внутри воркера.

### Этап 7. Продакшн-готовность (1–2 недели)

## 18. Чек-лист готовности к проду

**Функциональность**

- [ ] Повторная загрузка того же файла не создаёт дублей

- [ ] Все фоновые задачи проверены на идемпотентность

**Производительность**

## 19. Что стоит намеренно усложнить ради обучения

Эти вещи для pet-проекта избыточны, но именно они дают опыт, который отличает senior-код:

1. **Transactional outbox** вместо прямой отправки в брокер — учит думать о консистентности между хранилищами.
2. **Возобновляемая обработка по чанкам** вместо «упало — начинай сначала» — учит проектировать состояние долгих операций.
3. **Circuit breaker и bulkhead руками**, а не библиотекой (сначала руками, потом заменить библиотекой) — понимание, от чего они защищают.
4. **Курсорная пагинация** вместо `OFFSET` — сразу правильная привычка для больших таблиц.
5. **Партиционирование** таблицы истории цен — опыт работы с реально большими таблицами.
6. **Expand/contract миграции** — единственный способ деплоить без даунтайма.
7. **Нагрузочные тесты с фиксацией результатов** — учит измерять, а не угадывать.
8. **Профилирование** узких мест (`py-spy`, `EXPLAIN ANALYZE`) с записью до/после — самый ценный навык из всего списка.

## 20. Антипаттерны, которых нужно избежать

- Синхронные блокирующие вызовы в async-обработчике (`requests`, `time.sleep`, тяжёлый CPU) — блокируют весь event loop. CPU-нагрузка идёт в воркер или в `run_in_executor`.
- Чтение файла целиком в память (`file.read()`, `pd.read_csv` без `chunksize`).
- Передача объектов ORM в фоновые задачи вместо идентификаторов.
- `float` для денег.
- Бизнес-логика в роутерах — роутер только валидирует вход и вызывает сервис.
- Кэш как источник истины.
- Ретраи неидемпотентных операций.
- HTTP-запросы без таймаута.
- Отсутствие лимита на размер результата запроса.
- Задача, делающая всё сразу, без промежуточных контрольных точек.
- Создание HTTP-клиента или engine БД на каждый запрос.
